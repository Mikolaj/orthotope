TEMPLATE for $R-pair.txt. Copy it, fill it, delete this line and the two
below it -- but KEEP EVERY [SAME] AND [PAIR'S] MARKER in the note you
write. They cost a note nothing, and the next note is written with yours
open: a marked note shows at a glance which of its blocks would be a
COPYING ERROR to carry forward, which is the one thing the markers are
for and the one thing a session cannot tell by reading. Notes carried no
markers until 2026-09-01. What a next PREPARATION may skip is a
different question and a different set -- the chapter's reading list
answers it at item 10, naming the blocks by their leads. Every pair here is hand-built and its note is the only copy of
both recipes, so the note is written BEFORE either binary exists -- which
is also why it is a template and not a generator: what goes in it is a
person's, and only the slots are known in advance. Run 12's note carried
no commit and Run 14's carried none until the pair was built, both because
each note was written from scratch and nothing listed what a note owes.

BUT COPY FROM THE PREVIOUS NOTE AND NOT FROM HERE, and the ruling above
is about the DECISIONS and not about every line. Most of a note does not
vary from pair to pair, and a session that re-derives the invariant part
spends its attention where nothing is at stake. The blocks below are
marked [SAME] or [PAIR'S]:
  [SAME]    carried over from the previous note with the names changed
            and re-read rather than re-decided -- the naming rule, the
            launch lines, the riders, the counts recipe, the read-back
            block, the machine paragraph, the gate line, and the shape
            of the fill-in block. If one of these differs from the last
            note, that is a finding and the note says why.
  [PAIR'S]  written for this pair and never copied -- the entry point,
            what the pair measures and prices, why the basis is this
            recipe, the two recipes, the registrations and the roster.
            Copying one of these forward is how a note comes to describe
            the run before it.
A note that is mostly [SAME] is the normal state and not a lazy one. What
it must not be is mostly [SAME] in the [PAIR'S] blocks.

AND KEEP THE FIGURES OUT OF IT. A note is gitignored and goes with the
pair, so a session other than the one that wrote it cannot correct it:
Run 22's arms' session amended that run's registration in README.md at
ce8f5f7 and could not touch the note, which went on asserting a

ENTRY POINT FOR THE SESSION THAT RUNS THIS [PAIR'S]. It is a HANDOVER and
not a courtesy: a run is always two sessions, this file is the whole of
what crosses between them, and the session that reads it wrote none of it
and cannot ask you. So it goes here at the head, and it says, in this
order: which of the pre-run steps are SPENT and on what date; whether the
gate has run; what is
INHERITED and must not be repaid, naming each -- the gate, the smoke
sweep, the roster pass, the counts, anything else that cost machine time
-- and what is still OWED; and, last, WHAT THE PREPARATION LEARNED, which
is post-run step 9's four things met a day early -- a check that would
have caught an error, a computation improvised, a step skipped, a
capability found. Step 9 is the executing session's and that session was
not here, so this block is the only route those findings have. Those
lists are the interface; anything true of this run and in none of them is
lost. Then say outright whether anything here needs
a rebuild, since the offsets any registration is written against die
with one. INHERITED never reaches the binaries: both are built at step 2 of
this run's own preparation, never taken from a previous run, a probe, a
copy of the other half, or one binary run twice under two sets of flags.

AND SAY THAT NOTHING IN THE NOTE IS A REASON TO STOP [PAIR'S]. A preparation
that leaves a decision open states it plainly and states that it is not
a stop: Run 19's put a claims-retirement decision at this note's head in
the procedure's own stop-vocabulary, with *before the gate is paid*
beside it, and its first operator read it as a stop and lost the night
(2026-08-24). The test the procedure applies is whether the answer
changes what the machine does next; if it changes only the write-up, the
note says so here.

WHAT THIS PAIR MEASURES [PAIR'S]: one variable, named here, and nothing else. Say

HALVES: basis=<basis> other=<other>

NAMING THE HALVES [SAME]: neither name may begin with the other's followed by a
hyphen. install-tables.sh finds the basis's class JSONs by globbing
`$R-<basis>-*.json`, so a control called `<basis>-pa` is caught by it, and
`ls` sorts that file after the basis's own -- leaving the CONTROL half's
table in every class block under a driver that says every table comes from
the basis, with nothing downstream able to see it. Refused there since
2026-08-17 rather than left to the naming. Every half on record is
hyphen-free (`aligned`, `maxskip`, `maxskippa`, `lookrts`, `a1g`, `a32m`);
note that `maxskip`/`maxskippa` is a bare prefix and safe -- it is the
hyphen that collides.

THE SHIM [PAIR'S]: the commit align-as.py stood at, `git log -1 --format=%h --

HOW EACH HALF IS BUILT [PAIR'S], there being no builder here. Both from one source:

  $R-<basis>    cd here, then the full command, with --builddir, the
                regime, -fforce-recomp and every --ghc-options spelled out
  $R-<other>    the same with the one option that differs

  Spell the copy out too, or write it as `cp $(cabal list-bin micro

  one component of a recipe a later reader cannot reconstruct: notes
  before 2026-08-16 elide it as `db-r14a/.../micro`, which is not a
  command, in the file the README calls the only copy of both recipes.

  passes one.

LAUNCH [SAME]: every environment switch this pair wants, on the launch
line of BOTH the gate and the run. A pair whose instrument is switched on
by a variable is OFF unless the launch line sets it, and nothing
downstream notices -- the counts come out right, the gate passes, and the
registration the pair was built to answer comes back empty.
    <env> ./run-gate.sh $R
    <env> ./run-major.sh $R &
  The machine form of <env>, which run-evening.sh puts in front of every
  stage; `LAUNCH: none` for a pair that wants nothing:
LAUNCH: <NAME=value ...>
  Both drivers record what they were launched with, `launch env: ...`, in
  the gate's output and in the wallclock log, set or unset. Say here that
  the executor reads that line back rather than trusting the command it
  meant to type.

THE ALONE-LEG RIDERS [SAME], owed with the pair since Run 16 and out of

ANY OTHER GATE THIS NOTE SETS [SAME] MUST NAME WHAT DISCHARGES IT AND WHERE THE

THE FILL-IN BLOCK BELOW [SAME in shape, PAIR'S in content] IS OBSERVATIONS AND NOT INTERPRETATIONS. Record
what was measured -- the commits, the md5s, the byte counts, what agreed
with what -- and leave WHY to the write-up, where a checker can reach it and
an independent reader will re-derive it. Run 15's note wrote that the shim
was why its md5 did not reproduce Run 14's; that was an attribution made
before any evidence, it was inherited into the write-up as fact, and it was
wrong -- the shim is emission-neutral and a dependency relink was the cause.
An md5 that fails to reproduce is an OBSERVATION; what moved is a FINDING
and belongs where findings are checked.
